# M4 plan — Control and visibility

Spec reference: `agent-runtime-spec.md` §2 (budget enforcement with hard kill), §6 (the loop's
cancel/step/budget guards), §11 (observability), §13 (`/metrics`, `/v1/runs/:id/trace`), §14 M4,
§16 demo steps 3 and 5.

## Status: built (2026-09-13)

All six exit criteria are met, including tracing step two (the retroactive `agent.run` root) and
every item on the "cut if day 16 runs long" list. Verified live under compose: both processes
serve `/metrics`, Prometheus scrapes them (the worker by DNS discovery, so `--scale worker=2`
reports every replica), and one run produced one Jaeger trace containing `api.create_run` from
the API process and `agent.run` → `agent.run.attempt` → `agent.step` → `model.complete` /
`tool.invoke` from the worker. Both waterfalls are in the README
(`docs/trace-waterfall.png`, `docs/trace-crash.png`): a full trajectory, and the crash-resume
trace where worker A's attempt span is missing and the 10.4s band between the two workers is the
lease lapsing. What changed from the plan below while building:

- **`make demo-budget` needs no API key, which is the sharpest possible demonstration.** The
  pre-flight refusal happens before the provider is contacted, so a $0.02 budget against Opus
  terminates at `spent_usd = 0.0000` with `estimate_micro_usd: 406695` in the event — on a
  machine with no `ANTHROPIC_API_KEY` at all. The plan assumed this demo was live-only.
- **`make demo-cancel` found a hole in day 14's cancel path.** A cancel landing in the
  artificial `tool_delay_ms` — *before* `tool.Invoke` — returned the context error without
  writing a `tool_failed`, leaving the dangling `tool_requested` ADR-25 exists to prevent. The
  demo is where it showed up, because the delay is exactly the window a demo cancels into. Both
  interrupt paths now go through one `interruptedTool`, and `TestCancelBeforeTheToolRuns` is the
  regression test. Measured cancel latency: 0.69s and 1.17s against a tool call with 30 seconds
  left to run.
- **The worker's metrics listener degrades rather than refusing to start.** A port already in
  use is a warning: two workers on one host is `make crash-demo` and spec §2's lease demo, not a
  corner case. The crash demo gives its two workers `:9091` and `:9092` so both are scrapeable.
- **The worker's metrics port is published with no fixed host port** (`"9091"`, not
  `"9091:9091"`), which keeps `--scale worker=2` working *and* keeps `docker compose port worker
  9091` answering — the plan called for the first and assumed it cost the second.
- **`agentd healthz` is a subcommand.** The runtime image is distroless, so a compose
  healthcheck has no curl and no shell to run one from; the binary probes itself. Both services
  are health-checked now, not just the worker.
- **`model.Backend` resolves the metric labels before a call is made**, so a failed attempt is
  filed under the same `provider`/`model` as a successful one. Without it a Router's own name
  ("router") would have labelled every failure and every retry.
- **The API registers the loop's instruments too, and reports them as zero.** One instrument set
  per process is what makes a query work against either job and sum correctly across both.
- **The histogram buckets were worth setting explicitly, as predicted.** A real local model call
  measured 62.9s and a whole run 63.3s: with `prometheus.DefBuckets` both would have been `+Inf`.

## Goal

A run's cost is bounded *before* it is spent rather than audited after; a cancel takes effect in
seconds rather than at the next step boundary; and every run leaves one Jaeger trace and a set of
Prometheus counters that explain what it did — including across a `kill -9`.

The through-line of this milestone is that M1–M3 built the mechanisms and left the *controls*
half-done on purpose. The budget check fires after the money is gone. Cancel is honoured only
between steps. Four places in the repo already promise this milestone will fix something —
`docs/DECISIONS.md` ADR-7, ADR-12, and ADR-19's cost paragraph, plus the README's "Future work".
This is where those come due, and one of them (ADR-19) comes due with a different answer than it
expected: see Decision 3.

## What already exists (do not rebuild)

- `budget_usd` / `spent_usd` / `input_tokens` / `output_tokens` columns, micro-USD integer
  accounting (`model.Price`, `FormatUSD`, ADR-6), and `Provider.CostMicroUSD`. Cost is already
  committed in the same transaction as `model_responded` (`store.AppendModelResponse`).
- A post-hoc budget guard in `Loop.Execute` that appends `budget_exceeded` and finishes the run
  with the `budget_exceeded` status.
- `POST /v1/runs/:id/cancel`, the `cancel_requested` column, and the top-of-loop check that
  converts it into a `cancel_requested` event plus a cancelled `run_finished`.
- Jaeger in `deploy/docker-compose.yml` with `OTEL_EXPORTER_OTLP_ENDPOINT` already passed to both
  `api` and `worker`. Nothing reads it yet.
- Structured JSON logs already carrying `run_id`, `seq`, `step`, and `worker`.
- The reaper's log line, which ADR-7 promised would become a counter here.

Nothing in `internal/telemetry/` exists — the directory in the spec's §15 layout has never been
created. `go.opentelemetry.io/otel` is in `go.mod` only as an indirect dependency of
testcontainers.

## Exit criteria

1. **The budget is a ceiling, not a receipt.** A run whose *next* model call could carry it past
   `budget_usd` stops before making the call, with a `budget_exceeded` event that records the
   estimate and why. `make demo-budget` submits a run with `budget_usd: "0.02"` against Claude and
   shows it terminating without ever exceeding the number.
2. **Tool-internal model cost is attributed to the run.** `tool_succeeded` carries
   `cost_micro_usd` and token counts, the transaction that writes it bumps `spent_usd`, and
   `Reduce` folds it in, so the budget bounds *the run* rather than only the loop (ADR-19's open
   item; README "Future work" and `docs/plans/m3.md` both point here). The local-only
   `-rerank-model` restriction **stays**, but its justification changes from "we cannot measure
   this" to "we measured it and declined the spend" — see Decision 3.
3. **Cancel interrupts.** `POST /v1/runs/:id/cancel` on a run sitting inside a 10-minute model
   call or a 120-second sandbox call terminates it within the cancel poll interval plus the time
   the callee takes to honour the context, not at the next step. The event log stays well-formed:
   an interrupted tool call gets a `tool_failed`, not a dangling `tool_requested`.
4. **One trace per run, spanning processes and crashes.** The trace id is generated at submission,
   stored on the run, and reused by every worker that touches it, so `POST /v1/runs` and both
   halves of the crash demo land in one Jaeger waterfall. `GET /v1/runs/:id/trace` returns the deep
   link. The waterfall screenshot goes in the README, and the crash-resume trace goes next to it.
5. **Prometheus counters on both processes.** `/metrics` on the API and on the worker, covering
   §11's set: runs by terminal status, tool invocations by name and outcome, sandbox timeouts,
   tokens and dollars by model — plus lease reaps, cancellations, and budget terminations.
6. **Tests, README, ADRs.** Budget and cancel are integration-tested with a priced fake provider;
   the telemetry package is unit-tested against an in-memory span recorder so `make test` needs no
   Jaeger; ADR-22 through ADR-27; this plan gets its status block.

## Design

### Budgets: check before spending, not after

The current guard is `if state.SpentMicroUSD >= state.BudgetMicroUSD`. It is correct as an audit
and wrong as a ceiling: it can only notice an overrun that has already happened, and one call with
a large context and a 16k `max_tokens` can blow past a $0.05 budget by more than the budget.

Before each model call the loop prices the worst case and refuses if it does not fit:

```go
est := model.Usage{InputTokens: nextInputTokens(state), OutputTokens: int64(maxOut)}
if state.SpentMicroUSD + l.provider.CostMicroUSD(cfg.Model, est) > state.BudgetMicroUSD {
    // budget_exceeded{reason: "would_exceed", ...}
}
```

Two pieces are new:

- **`nextInputTokens`** avoids needing a tokenizer. The previous step's `input_tokens` is a real
  number the provider measured, and the only thing added since is the tool results now sitting in
  the message list, whose size is known exactly. So the estimate is `state.LastInputTokens +
  newChars/4`, and on step one a plain `chars/4` over the system prompt, goal, and tool schemas.
  `Reduce` grows a `LastInputTokens` field to carry the first term. The estimate deliberately
  ignores prompt-cache reads, which are cheaper — an estimate that errs high is the right
  direction for a ceiling.
- **`Provider.MaxOutputTokens(model string) int`** joins `CostMicroUSD` on the interface. The
  loop needs a number for the output term when `agent_config.max_tokens` is unset; Anthropic has
  `DefaultMaxTokens = 16000` and the local provider currently passes `0` through and lets the
  server decide. `Router` delegates by the same predicate it routes with.

`BudgetExceededPayload` gains `Reason` (`"spent"` or `"would_exceed"`), `EstimateMicroUSD`,
`EstimatedInputTokens`, and `MaxOutputTokens`. Additive, so existing logs still reduce. Both
guards stay: the pre-flight check is the ceiling, the post-hoc check is the backstop for a call
that came in over its estimate.

Honest about the cost of this (ADR-22): the runtime will sometimes refuse a call it could in fact
have afforded, because the worst case is what it prices. For a *hard* budget that is the correct
trade — the alternative failure mode is a bill. And with a local model every price is zero, so the
pre-flight branch never fires locally; it is exercised by Anthropic in `make demo-budget` and by a
priced fake provider in tests.

### Tool-internal model cost

M3 shipped an LLM reranker whose model calls happen *inside* `search_corpus`, so its tokens never
reach `spent_usd`. That is a soundness hole, not a cost question: the budget stopped bounding the
*run* and started bounding only the *loop*. M3 plugged it with policy — refuse any rerank model
that routes to a paid provider ([`retrieval.go:99`](../../cmd/agentd/retrieval.go#L99)) — which is
sound while tool-internal spend is exactly $0, and silently unsound the moment any future tool
calls a paid model. M6's MCP adapter will expose arbitrary third-party tools; some of them will.

So the mechanism ships regardless of whether the policy is relaxed:

- `tools.Result` gains a `Cost` struct — `{MicroUSD, InputTokens, OutputTokens int64; Model
  string}` — kept local to the `tools` package so `tools` does not grow a dependency on `model`.
- `rerank.Reranker.Rerank` returns usage alongside its scores. One real implementation plus
  `Noop`, so changing the interface is cheap. `retrieval.Searcher` sums it into `retrieval.Result`
  and `corpus.Search` copies it onto `tools.Result`.
- `ToolSucceededPayload` gains `CostMicroUSD`, `InputTokens`, `OutputTokens`, `CostModel`.
- `store.CompleteToolCall` takes the same three counter arguments `AppendModelResponse` already
  takes and runs the same `UPDATE` in the same transaction as the event. Factor the counter bump
  into one helper so there is a single place where the log and the counters can disagree.
- `Reduce` adds tool cost into `SpentMicroUSD` and the token counters.
- `cmd/agentd/retrieval.go` is **unchanged**: `buildReranker` keeps its `*local.Provider`
  parameter and the refusal stays. What changes is the error message and the docs around it,
  which currently say the restriction exists because cost is unattributed. After M4 that is false.
  The refusal's reason becomes the measured cost below, and README "Future work", ADR-19's cost
  note, and `m3.md`'s deferral list are rewritten to say the mechanism landed and the policy was
  kept deliberately — not that the item is still outstanding.

Two pieces of honesty for ADR-22:

**Tool cost is committed after the tool runs**, so a tool can overshoot within a single call. With
the local-only policy in force the overshoot is exactly $0 today, so this is latent rather than
live — but it becomes real with the first paid MCP tool in M6, and the bound is one tool call's
spend. Pre-flighting it would mean the registry predicting each tool's cost before invoking it,
which is not worth building for a hole this size. The budget is a *ceiling* on model calls and an
*audit* on tool calls, and the README says so in those words.

**The counters can now move without a `model_responded` event.** Anyone reading `spent_usd` and
summing `model_responded` costs to check it will get a mismatch unless they also sum
`tool_succeeded`. Worth one line in the README's event-table section, since the invariant "the
counters equal the fold of the log" is one M1 advertised.

### Cancellation that interrupts

Ownership split: the **Worker** owns leases, the **Loop** owns cancellation. `Loop.Execute` derives
its own context and runs a watcher next to the worker's heartbeat:

```go
execCtx, interrupt := context.WithCancel(ctx)
defer interrupt()
cancelled := l.watchCancel(execCtx, run.ID, interrupt)   // polls runs.cancel_requested
```

When the watcher sees the flag it cancels `execCtx`. The in-flight `provider.Complete` or
`tool.Invoke` returns `ctx.Err()`, the loop unwinds, and a check at the top distinguishes three
cases that currently all look like `context.Canceled`:

| Cause | How it is known | What happens |
|---|---|---|
| Cancel requested | the watcher's channel is closed | finish `cancelled` under `context.WithoutCancel(ctx)` |
| Worker shutting down | the *parent* `ctx.Err() != nil` | return `ctx.Err()`; the lease is left to expire (unchanged) |
| Lease lost | the heartbeat cancelled it; fenced writes return `ErrLeaseLost` | return; another worker owns the run (unchanged) |

Today the worker infers these from `ctx.Err()` and from `finish` happening to fail with
`ErrLeaseLost`. Making the reason explicit is a small refactor that this milestone needs anyway,
and it removes the indirection.

Two details that keep the log well-formed:

- **An interrupted tool call gets a `tool_failed`** (`error: "run cancelled"`, `retryable: false`)
  written under a non-cancelled context, rather than leaving a `tool_requested` with no
  completion. The ledger row moves to `failed` in the same transaction. Without this the run's
  final log ends with an open tool use, which `Reduce` tolerates but which no other path produces.
- **An interrupted model call leaves a dangling `model_requested`**, which is exactly the state a
  crash mid-call produces and which `Reduce` already models as `ModelInFlight`. Tokens spent on
  that call are lost — the same caveat the loop already documents for empty responses. Say it in
  the README rather than pretending otherwise.

**Cancelling a queued run needs no code and should not get any.** The event log requires
`run_started` first, and only a worker can resolve the agent-config snapshot that goes in it. So a
queued cancel is claimed by a worker, which writes `run_started` → `cancel_requested` →
`run_finished` in milliseconds and moves on. That already works; M4 adds the test that says so and
one line in the README, because "why doesn't the API just finish it" is the obvious question.

Latency bound: `-cancel-poll` (default 1s) plus however long the callee takes to honour the
context. The sandbox already has a `docker kill` fallback behind its context, so a runaway script
dies promptly. `make demo-cancel` measures wall time from the `POST` to the `run_finished` frame
on the SSE stream and prints it.

The poll costs one indexed single-row query per second per *running* run, and `claimAndExecute`
is sequential, so that is 1 qps per worker. ADR-25 should record the zero-cost floor it was chosen
over: the heartbeat already writes to that exact row every `lease/3` (20s by default), so
`UPDATE … RETURNING cancel_requested` would give cancel detection for no additional query at all.
The dedicated poll buys sub-second latency instead of ~20s, which is worth one query per second
because cancel latency is a number the demo prints. `LISTEN/NOTIFY` remains the real upgrade and
would also retire the SSE tail's 200ms poll — the more valuable target, since that one is per
connected client rather than per worker.

### Tracing across processes and crashes

This is the part of M4 with a real design problem in it. §11 says "one trace per run", but a run
is submitted by one process, executed by another, and may be executed by a *third* after a
`kill -9`. In-process context propagation cannot span that. The trace identity has to be durable.

**Migration 0003** adds two nullable columns:

```sql
ALTER TABLE runs
  ADD COLUMN trace_id     TEXT,
  ADD COLUMN root_span_id TEXT;
```

`api.createRun` generates both, stores them on the row, and records its own `api.create_run` span
under them. Every worker that claims the run rebuilds the parent with
`trace.ContextWithRemoteSpanContext(ctx, trace.NewSpanContext(...))`, so all of its spans land in
the run's trace regardless of which process or which attempt produced them. Runs created before
M4 have null columns and `/trace` returns 404 for them.

**The span tree:**

| Span | Emitted by | Key attributes |
|---|---|---|
| `agent.run` | the worker that writes the terminal event, retroactively | `agentd.run.status`, `agentd.run.steps`, tokens, `agentd.cost_micro_usd`, model, tool allowlist |
| `api.create_run` | the API at submission | `agentd.budget_usd`, `agentd.max_steps`, tool count |
| `agent.run.attempt` | each worker claim, child of `agent.run` | `agentd.worker.owner`, `agentd.run.resumed`, `agentd.events.replayed` |
| `agent.step` | each loop iteration | `agentd.step` |
| `model.complete` | `modelStep`, including retries | `gen_ai.system`, `gen_ai.request.model`, `gen_ai.usage.input_tokens` / `.output_tokens`, cache read/write, stop reason, `agentd.attempt`, `agentd.cost_micro_usd` |
| `tool.invoke` | `runTool` | `agentd.tool.name`, `agentd.tool.trust_tier`, `agentd.seq`, `agentd.tool.exit_code`, `agentd.tool.replayed`, outcome |
| `sandbox.exec` | the Docker executor, under `tool.invoke` | `agentd.sandbox.exit_code`, `agentd.sandbox.timed_out`, image, duration |
| `retrieval.search` | `Searcher.Search`, under `tool.invoke` | `agentd.retrieval.mode`, `k`, `candidates`, vector/lexical hit counts, `agentd.rerank.degraded` |
| `retrieval.embed` / `.vector` / `.lexical` / `.rerank` | the search stages | duration only |

The GenAI attribute names come from the OTel semantic conventions where they exist; the rest are
namespaced `agentd.*`. §11 only asks for `retrieval.search`, but the four stage children are ~10
lines and make the reranker's dominance of search latency visible in the waterfall, which is
exactly the number M3 asked the README to be honest about.

**Making `agent.run` a real root span.** A span is only exported when it *ends*, so a root span
that lives as long as the run cannot survive the crash it is meant to illustrate. Instead the
worker that writes the terminal event emits `agent.run` retroactively — `trace.WithTimestamp(run.
CreatedAt)` for the start, now for the end, and the stored `root_span_id` so every attempt from
every worker already points at it. Setting the span id explicitly needs a custom
`sdk/trace.IDGenerator` that reads an id planted on the context; it is a documented extension
point and about thirty lines. That is ADR-24.

**Build this as two separable steps, because the second one can be abandoned.** Step one is the
durable trace id alone: store it, rebuild a remote parent from it, and let each attempt be a
root-level span in a multi-root trace, which Jaeger renders fine. That already delivers one trace
per run, the deep link, and the crash gap. Step two adds the retroactive `agent.run` on top. If
the ID generator fights back on day 15, the fallback is deleting one span emission rather than
redesigning — the trace stays correct without it, just without a summary bar.

**The hazard in step two, stated so it does not get rediscovered later:** the `IDGenerator` is a
provider-wide hook consulted for *every* span creation. If the context carrying the planted span
id leaks past the single `tracer.Start` call it was made for, several spans receive the same span
id and the trace is corrupt. Plant it on a context used for exactly one `Start` and never pass
that context downward; the unit test should assert that a second `Start` on a derived context gets
a random id.

**A limit worth knowing up front:** a run that never finishes never gets a root span, because
nothing emits it. For a hung run — the case you most want to inspect — the trace degrades to the
step-one shape. That is acceptable (the children are still queryable by trace id, so the deep link
works), and it is the reason the durable span table in option (f) exists in real systems. Building
one here would duplicate what the event log already records.

**Three things the trace will do that look wrong and are not** — all of which go in the README
next to the screenshot, because each of them is a question an interviewer asks:

1. **A crashed attempt has no `agent.run.attempt` span.** The process died before `span.End()`, so
   it was never exported. Its already-completed children *were* exported and appear with a missing
   parent; Jaeger renders them. That gap in the waterfall is the crash, drawn accurately.
2. **The root span ends before its children do** — it is emitted last but timestamped from
   `created_at`, and attempts overlap it correctly. Long children under a parent that closes early
   is normal for asynchronous work.
3. **A run that never finishes has no root span.** Children are still queryable by trace id, so
   the deep link still works.

The strictly-idiomatic OTel answer for work that crosses a queue is *span links* between separate
traces, not a shared trace id. That is the deviation ADR-24 defends: §11 asks for one trace per
run and §13 for a single deep link, and two traces joined by a link delivers neither.

**`internal/telemetry`:**

```
internal/telemetry/
  trace.go      Init(ctx, Config) (*Telemetry, error); OTLP/HTTP exporter, resource, shutdown
  idgen.go      IDGenerator that honours a span id planted on the context
  span.go       small helpers: StartRun, StartStep, RecordUsage, End(err)
  metrics.go    the Prometheus registry and instruments (below)
  slog.go       a slog.Handler wrapper that adds trace_id/span_id from the context
  trace_test.go unit tests against sdk/trace/tracetest.SpanRecorder — no Jaeger, no network
```

With no `OTEL_EXPORTER_OTLP_ENDPOINT` set, `Init` returns a no-op provider. This matters more than
it sounds: `make test`, `agentd ingest`, `agentd eval`, and anyone running the binary outside
compose must not need a collector, and an unreachable collector must be a warning rather than a
fatal — the exporter retries in the background on its own.

**Log correlation.** A `slog.Handler` wrapper pulls `trace_id` and `span_id` off the context and
adds them to every line, so a log line and a waterfall span can be matched up. Cheap, and it is
the other half of §11's "structured logs with `run_id` and `seq` on every line".

**`GET /v1/runs/:id/trace`** returns `{"trace_id": "...", "url": "http://localhost:16686/trace/..."}`,
with the UI base from `-jaeger-ui` / `AGENTD_JAEGER_UI`. 404 when the run predates M4 or tracing
was off — the endpoint should not invent a link to a trace that does not exist.

### Metrics

`internal/telemetry/metrics.go`, on `prometheus/client_golang` (ADR-26), with a registry per
process rather than the default global one, and instruments hung off a `Metrics` struct that gets
injected into the loop, the worker, the sandbox, the searcher, and the API. No package-level
globals: two workers in one test process must not fight over `MustRegister`.

**Set histogram buckets explicitly — the defaults are wrong for this workload.**
`prometheus.DefBuckets` tops out at 10 seconds, while M3's README documents the local reranker at
10–30s per search and `-model-timeout` defaults to 10 minutes. With the defaults, nearly every
model and rerank observation lands in `+Inf` and the histograms are decorative. Use something like
`.1, .25, .5, 1, 2.5, 5, 10, 30, 60, 120, 300` for the model, tool, and retrieval histograms.

| Metric | Type | Labels |
|---|---|---|
| `agentd_runs_finished_total` | counter | `status` |
| `agentd_run_duration_seconds` | histogram | `status` |
| `agentd_runs_claimed_total` | counter | `resumed` |
| `agentd_steps_total` | counter | — |
| `agentd_model_calls_total` | counter | `provider`, `model`, `outcome` (`ok`\|`retried`\|`failed`\|`non_retryable`) |
| `agentd_model_tokens_total` | counter | `provider`, `model`, `kind` (`input`\|`output`\|`cache_read`\|`cache_write`) |
| `agentd_model_cost_micro_usd_total` | counter | `provider`, `model` |
| `agentd_model_latency_seconds` | histogram | `provider`, `model` |
| `agentd_tool_invocations_total` | counter | `tool`, `outcome` (`succeeded`\|`failed`\|`rejected`\|`replayed`) |
| `agentd_tool_duration_seconds` | histogram | `tool` |
| `agentd_sandbox_timeouts_total`, `agentd_sandbox_orphans_swept_total` | counter | — |
| `agentd_retrieval_searches_total` | counter | `mode`, `degraded` |
| `agentd_retrieval_duration_seconds` | histogram | `stage` |
| `agentd_leases_reaped_total`, `agentd_leases_lost_total` | counter | — |
| `agentd_budget_terminations_total` | counter | `reason` (`spent`\|`would_exceed`) |
| `agentd_cancellations_total` | counter | `phase` (`idle`\|`model`\|`tool`) |
| `agentd_http_requests_total` | counter | `route`, `method`, `code` |
| `agentd_sse_streams_active` | gauge | — |

`agentd_leases_reaped_total` is ADR-7's promise coming due; `agentd_model_calls_total{outcome=
"non_retryable"}` is ADR-12's, which also means M4 should land the typed non-retryable provider
error that ADR-12 called "a small M4 follow-up once the loop grows a metric for it" — a
`model.NonRetryable` wrapper that `local` and `anthropic` return for refusals, unknown models, and
authentication failures, so `modelStep` stops burning three attempts on an error that cannot
succeed.

**Postgres-backed gauges.** Counters reset when a process restarts, which makes "how many runs
have ever failed" a question the API cannot answer after a deploy. The API also registers a
`prometheus.Collector` that answers from the database on scrape: `agentd_runs{status}` from one
indexed `GROUP BY`, and `agentd_runs_oldest_queued_age_seconds` as the queue-depth signal that
actually pages someone. Process counters for events, database gauges for state; ADR-26 says why
both.

**Cardinality is a hard rule, stated in the code and the ADR:** never `run_id`, never `goal`,
never a model-supplied string as a label. `tool` is bounded by the registry, `model` and
`provider` by configuration, `status` and `outcome` by constants.

**Where they are served.** The API exposes `/metrics` on its existing listener. The worker has no
HTTP server, so it gets a small one: `-metrics-addr` (default `:9091`), serving `/metrics` and
`/healthz`, which is also the worker liveness probe compose has been missing. A `prometheus`
service scraping both is added so the counters are demoable rather than a text endpoint nobody
opens. That service is the first thing to cut.

**Do not publish the worker's metrics port to the host.** Spec §2 requires running two workers to
prove leases work, and `docker compose up --scale worker=2` fails on a port collision the moment a
fixed host port is mapped. Prometheus scrapes it inside the compose network by service DNS, which
resolves to every replica; `docker compose port worker 9091` gets an ad-hoc host address when one
is needed. This is cheap to get right on day 16 and annoying to discover there.

### Wiring

Flags and env, following the existing pattern in `cmd/agentd/main.go`:

## Explicitly not in M4

Cassette recording and replay, the YAML suite, `make eval`, and the scorecard (M5) — M4 ships the
budget and cancellation *integration tests* that M5's `BUDGET` and `RESILIENCE` rows will wrap, but
not the harness. Poisoned documents and the `INJECTION` category (M5). The MCP adapter, the
single-page trajectory viewer, and `POST /v1/corpus/ingest` (M6). The OTel *logs* signal — `slog`
to stdout stays the log path, with trace ids for correlation. Grafana dashboards, an OTel Collector,
and tail-based sampling: Jaeger direct and `AlwaysSample` are right at this scale, and the
production shape gets a paragraph in the README instead of a container. `otelpgx`-style tracing of
individual SQL statements — the interesting latency here is models and sandboxes, and per-query
spans would bury it. Per-tenant or global budgets, and topping up a running run's budget (both need
the multi-tenancy that §2 puts out of scope). Pre-flighting *tool* cost, as argued above.

A hosted reranker (Decision 3) — the *mechanism* that would make it safe ships here, the *policy*
does not change. With it, the rerank sub-budget that would bound a search-heavy run's tool spend
is also unnecessary; it becomes live the first time a paid tool is allowed, most likely alongside
M6's MCP adapter, and the reranker's existing degrade-to-fused-order path is the seam it would
use.

## Decisions (settled 2026-09-11, before implementation)

Taken up front so they can be argued with before there is code to defend. Each names what was
chosen, what it was chosen over, and the consequence that makes it worth writing down.

1. **Metrics go through `prometheus/client_golang`, not the OTel metric SDK.** (ADR-26)
   Traces use OTel; metrics do not. The deciding factor is that the unusual half of this problem is
   the Postgres-backed gauge — a scrape-time read from an external source of truth — and
   `prometheus.Collector` is the abstraction built for exactly that. The event half is commodity in
   either library. Two supporting facts: `testutil.CollectAndCompare` diffs exposition text, which
   makes the metrics test row worth writing, and `otel/exporters/prometheus` depends on
   `client_golang` transitively, so "one instrumentation API" would mean both dependency trees, not
   one. *Given up:* exporter portability, and exemplars linking histogram buckets to trace ids come
   less automatically.

2. **One trace per run via a durable trace id, with `agent.run` emitted retroactively at finish.**
   (ADR-24) Chosen over span links with separate traces (the OTel convention for queue-crossing
   work, which would give §13 no single deep link and split the crash demo across two waterfalls),
   over no root span at all, and over a root emitted at submission — that last one has all the same
   plumbing but ends before the run starts, so it can carry neither the real duration nor the final
   status. Build it as two steps, as above; step two is droppable. *Given up:* a hung run still
   gets no root, and the `IDGenerator` is a provider-wide hook that must not leak its planted id.

3. **The reranker stays local-only; the cost mechanism ships anyway.** (ADR-19 amendment, ADR-22)
   Attribution is mandatory — it is what makes the budget bound the run rather than the loop, and
   M6's MCP tools will need it. The *policy* is kept: `-rerank-model` still refuses anything that
   routes to a paid provider. What changes is why. Measured, a hosted reranker costs roughly 11,000
   input and 500 output tokens per search — about **$0.04 at Sonnet-class rates, or ~20% on top of
   a six-step research run**, so three searches is roughly +65%. That is affordable and was still
   declined, in exchange for runs that stay cheap by construction and a restriction that needs no
   per-run reasoning. *Given up:* the hosted reranker's latency win is real and unclaimed — M3
   documents the local reranker at 10–30s per search, the slowest step in a research run, where a
   hosted model with `Parallel: 4` would finish in seconds. Revisit if search latency becomes the
   complaint.

4. **Cancellation uses a dedicated 1s poll during execution.** (ADR-25) Chosen over piggybacking
   the existing heartbeat, which would be free but caps latency at `lease/3` ≈ 20s, and over
   `LISTEN/NOTIFY`, which is the real fix and a milestone of its own. The justification is that
   cancel latency is a number `make demo-cancel` prints, and 1 qps per worker is not a cost. *The
   load-bearing part of this work is not the interval* — it is making the three cancellation
   reasons explicit in the worker's unwind instead of inferring them from `ctx.Err()`.

5. **The worker gets its own HTTP listener for `/metrics` and `/healthz`.** Chosen over a
   Pushgateway, which exists for jobs that exit before being scraped and would keep a dead worker's
   numbers alive forever, and over routing worker metrics through Postgres. The real content of
   this decision is the wiring consequence: **the port is not published to the host**, because §2's
   two-worker lease demo runs `--scale worker=2` and a fixed host port collides on the second
   replica.
