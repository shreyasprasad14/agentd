# M2 plan — Sandbox

Spec reference: `agent-runtime-spec.md` §7 (sandbox executor), §8 (the `python` tool, shipped as `run_python`), §10 (per-run
capability grants), §12 `SAFETY` row, §14 M2.

## Status: implemented (2026-09-09)

Everything below is done and green under `make test`, including the SAFETY set against the real
Docker daemon. Verified live against Ollama (`qwen2.5:7b`) with the goal from `make demo-python`:
the model's first script imported `dateutil`, the stdlib-only sandbox returned exit 1 with the
traceback as data, the model rewrote it with the standard library, got `2026-10-15` (matching
`compute_deadline`), and called `finish` with it. What changed from the plan below while building:

- **The tool is `run_python`, not `python`.** Ollama 0.33 reserves the name `python` for its own
  builtin tool and silently drops any tool call by that name: the raw model output was a
  well-formed `<tool_call>` every time, the OpenAI-compatible and native endpoints both returned
  empty content with `finish_reason: stop`, and the same request with the tool renamed parsed 5
  of 6 times (0 of 12 as `python`, even for `print("hello")`). Renaming was the right trade over
  a name-aliasing layer in the local provider.
- **An empty model response is retried, then fails the run.** Chasing the above exposed that a
  response with no text and no tool call finished the run `succeeded` with an empty answer. The
  loop now treats it like a transport error (retry inside the same model step, up to three
  attempts) and fails the run with a clear message if it persists. `TestLoopEmptyModelResponseIsRetried`
  covers both halves. This is the one loop change in M2.
- **Inputs go through an anonymous volume, not a copy into the rootfs.** The daemon refuses
  `CopyToContainer` into a read-only rootfs (`container rootfs is marked read-only`); the plan's
  wording below is kept, ADR-15 has the reasoning, and the safety test asserts `/work/in` gives
  `EACCES` to the sandboxed process.
- **The worker finds the daemon like the CLI does.** The SDK only knows `DOCKER_HOST` and the
  default socket; Docker Desktop on macOS uses a per-user socket named by the current CLI
  context. `sandbox.DockerHost()` resolves `DOCKER_HOST`, then the context, then the default.
- **Egress assertion loosened from "only `lo` exists" to "only `lo` is up, no routes, no
  non-loopback IPv6".** Docker Desktop's kernel stamps down, addressless tunnel stubs
  (`tunl0`, `gre0`, `sit0`, …) into every new netns.

Not done here: the crash-demo GIF is unchanged (it uses `compute_deadline`); a `run_python`
variant of the crash demo is a natural M5 RESILIENCE case since the sandbox container is the
side effect that gets re-executed.

## Goal

Every tool call that runs untrusted code goes into a fresh container with the full flag set from
§7, a wall-clock timeout the worker enforces, and output truncated to a fixed byte budget before it
reaches the context window. Ship the `run_python` tool on top of it, and safety tests that prove
egress is blocked, a fork bomb is contained, the rootfs is read-only, and the process is
unprivileged. Exit criteria:

1. A run whose model calls `run_python` completes through the same worker as before, with the script's
   stdout in `tool_succeeded.result` and the container's exit code in `tool_succeeded.exit_code`.
2. A script that sleeps past its timeout is killed, the container is removed, and the model sees
   `timed_out: true`.
3. Integration tests against the real Docker daemon cover the §12 `SAFETY` checks: network egress,
   fork bomb, filesystem writes outside `/tmp`, plus memory cap, tmpfs cap, non-root, no
   capabilities, `no-new-privileges`, output truncation, timeout, cancellation, and cleanup.
4. README paragraph with the sandbox tradeoff writeup, ADRs, `docs/SECURITY.md`, this plan.

### Executor

```go
type Spec struct {
    Cmd     []string
    Stdin   []byte
    Files   map[string][]byte // placed under /work/in before start, read-only at runtime
    Timeout time.Duration     // clamped to Limits.MaxTimeout; 0 → Limits.DefaultTimeout
    Labels  map[string]string // run_id, seq, tool: for the orphan sweep and for docker ps
}
type Output struct {
    Stdout, Stderr                   []byte
    StdoutTruncated, StderrTruncated bool
    ExitCode                         int
    TimedOut, OOMKilled              bool
    Duration                         time.Duration
}
type Executor interface {
    Run(ctx context.Context, spec Spec) (*Output, error)
}
```

`Run` returns an error only when the sandbox itself failed (daemon unreachable, image missing,
create/start refused). A script that exits nonzero, is OOM-killed, or hits the timeout is a
successful `Run` with those facts in `Output`, because the model needs to see them as data and
decide what to do; the loop records them in `tool_succeeded` with the exit code.

Container configuration is the §7 command, field for field:

| `docker run` flag | Engine API |
|---|---|
| `--rm` | explicit `ContainerRemove{Force}` in a defer on a background context (AutoRemove races the attach stream) |
| `--network=none` | `HostConfig.NetworkMode = "none"` |
| `--memory=512m --memory-swap=512m` | `Resources.Memory = Resources.MemorySwap = 512 MiB` (no swap) |
| `--cpus=1` | `Resources.NanoCPUs = 1e9` |
| `--pids-limit=128` | `Resources.PidsLimit = 128` |
| `--read-only` | `HostConfig.ReadonlyRootfs` |
| `--tmpfs /tmp:size=64m,exec` | `HostConfig.Tmpfs["/tmp"] = "rw,exec,nosuid,size=64m"` |
| `--cap-drop=ALL` | `HostConfig.CapDrop = ["ALL"]` |
| `--security-opt=no-new-privileges` | `HostConfig.SecurityOpt` |
| `--user 65534:65534` | `Config.User` |
| (not a flag) | `LogConfig.Type = "none"`: output is captured over the attach stream, never written to the daemon's log files, so a flood cannot fill the host disk |

Input files reach the container through `CopyToContainer` (a tar archive into `/work/in`) on the
created-but-not-started container, not a bind mount. A bind mount needs a path that exists on the
Docker *host*, which is wrong as soon as the worker itself runs in a container (compose) and talks
to the daemon over the socket. The archive copy works from anywhere the API is reachable.

Timeout: `ContainerWait` under `context.WithTimeout`. On expiry, `ContainerKill(SIGKILL)` on a
background context, a second short wait for the exit code (137), and `TimedOut = true`. On the
caller's context being cancelled (worker shutdown), the same kill and remove, then `ctx.Err()` so
the loop records nothing and the next worker re-executes.

Output: the attach stream is demultiplexed with `stdcopy` into two `limitWriter`s that keep the
first N bytes and count the rest, so a script printing gigabytes costs the worker N bytes of
memory and the model sees `stdout_truncated: true`.

Orphans: every container carries `agentd.sandbox=true`, `agentd.run_id`, `agentd.seq`,
`agentd.tool` labels. A worker that is `kill -9`'d mid-call leaves its container running until the
sandbox timeout fires inside… nothing, because the timeout lives in the dead worker. So each worker
sweeps on boot: any `agentd.sandbox` container older than `MaxTimeout + grace` cannot be live and is
force-removed. Younger ones may belong to a healthy sibling worker and are left alone.

### The `run_python` tool

```
name:        run_python
trust tier:  sandboxed
args:        code (string, required, ≤ 64 KiB)
             stdin (string, ≤ 64 KiB)
             files (object of name → content, names are plain file names, ≤ 16 files)
             timeout_seconds (integer, 1 … Limits.MaxTimeout)
result:      {stdout, stderr, exit_code, timed_out, oom_killed, stdout_truncated,
              stderr_truncated, duration_ms}
```

`code` is written to `/work/in/main.py` and run as `python3 /work/in/main.py`, so tracebacks
carry real line numbers and stdin is free for the script's own input. Standard library only: the
image has no pip and the container has no network, and the description says so.

In `serve` mode the tool is registered without an executor so `/v1/tools` lists it and the
allowlist accepts it; only `work` builds the Docker executor. If a worker cannot reach Docker, it
logs a warning at boot and every `run_python` call fails as a retryable `tool_failed`, which the model
sees; the worker keeps serving runs that never call it.

## Test matrix

| Test | Kind | Asserts |
|---|---|---|
| `limitwriter_test.go` | unit | keeps the first N bytes, counts the rest, flags truncation exactly at the boundary |
| `python_test.go` | unit, fake executor | spec: cmd, `main.py` + files, labels from the invocation, timeout default and clamp; result: nonzero exit is a Result not an error, timeout and truncation flags carried, executor error is an error; schema: missing `code`, out-of-range `timeout_seconds`, bad file name rejected by the registry |
| `docker_test.go` echo | integration | stdout, stderr, exit code, duration, container removed afterwards |
| `docker_test.go` stdin / files | integration | script reads stdin; reads `/work/in/<name>`; `/work/in` is read-only |
| `docker_test.go` truncation | integration | 1 MiB of stdout → `len(Stdout) == MaxOutputBytes`, `StdoutTruncated` |
| `docker_test.go` timeout | integration | `sleep 60` with a 2 s timeout returns in well under 10 s with `TimedOut`, exit 137, container gone |
| `docker_test.go` cancel | integration | cancelling ctx mid-run returns `context.Canceled` and the container is gone |
| `docker_test.go` sweep | integration | a labelled leftover is removed by `SweepOrphans(0)`; an unlabelled container is not |
| `safety_test.go` egress | integration | TCP connect to 1.1.1.1:80 and DNS both fail; only `lo` exists |
| `safety_test.go` fork bomb | integration | fork fails with `EAGAIN` inside the pids limit; returns within the timeout; stderr shows the failure |
| `safety_test.go` filesystem | integration | writes to `/`, `/usr`, `/etc`, `/work/in` fail with `EROFS`; `/tmp` works; 100 MiB into `/tmp` fails with `ENOSPC` |
| `safety_test.go` privileges | integration | uid/gid 65534, `CapEff` all zero, `NoNewPrivs: 1` |
| `safety_test.go` memory | integration | allocating 1 GiB is killed (`OOMKilled` or `MemoryError`), never prints success |
| `loop_test.go` python | integration, fake executor | the loop carries the sandbox exit code into `tool_succeeded.exit_code` and the stdout into the tool_result the next model call sees |

The Docker integration tests build `agentd/sandbox:python` from `deploy/sandbox` once per test
binary with the `docker` CLI and skip if the CLI or daemon is missing. They are separate from the
testcontainers Postgres fixture: `make test-sandbox` runs only them.

## Explicitly not in M2

Output file collection from `/tmp/out` (stdout is the only channel; `/tmp` is a tmpfs that dies
with the container, so collecting from it needs a volume and a `CopyFromContainer`, which nothing
needs yet), a network-enabled trust tier (§7 says document it as a separate tier; there is no
tool that needs it), gVisor / Firecracker runtimes (`HostConfig.Runtime` is one field away; see
the README tradeoff section), a warm container pool (cold start is ~300 ms on Docker Desktop,
fine for a legal-research agent), OTel spans around `Run` (M4).
