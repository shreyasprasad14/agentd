Spec reference: `agent-runtime-spec.md` §8 (the MCP client adapter), §13 (the SSE replay contract,

## Status: built (2026-09-15), corpus measured (2026-09-16)

### The corpus measurement, measured

| mode | recall@8 | MRR | wall time |
|---|---|---|---|
| vector | 1.000 | 0.963 | 2.5 s |
| bm25 | 0.950 | 0.830 | 2.3 s |
| hybrid | 1.000 | **0.988** | 2.8 s |
| hybrid+rerank | 1.000 | 0.971 | 1,984 s |

84 SCOTUS cases, 13,114 chunks, 40 labeled queries. Two results, one of them negative:

- **Rank fusion earns its place, on MRR.** Hybrid beats both inputs — 0.988 against 0.963 and
  0.830. This is the vector-vs-hybrid delta the fixture could never show.
- **The LLM reranker is a measured loss.** It costs 713× the wall time of hybrid and *lowers* MRR,
  0.988 → 0.971. The plan said to report whatever came out, and specifically anticipated this:
  it converts [ADR-23](../DECISIONS.md)'s local-only rerank policy from a price argument into a
  measured one. A 7B model re-ordering eight already-good hits mostly finds new ways to be wrong.
- **Recall@k still saturates, and the corpus size is why.** Not the duplicates — see below.

Five of six exit criteria met. The MCP adapter, the viewer, `GET /v1/runs`, the CLI wiring, the
docs and ADRs 34–38 are shipped and green; `POST /v1/corpus/ingest` was cut on purpose (see
Decisions). What changed from the plan while building:

- **A cap in the wrong slot, which only a manifest showed.** The HTTP transport's `MaxEventSize`
  was `MaxResultBytes` — a bound on one result, sitting where every message passes. With
  `MaxSchemaBytes` larger than `MaxResultBytes`, a server whose schema the adapter would accept
  could not be listed at all. The stdio tests passed throughout, which is the argument for ADR-38:
  a bound that lives in the transport gives one hostile server two blast radii.
- **The poisoned-description eval needed a new exposure channel, not a new case.** `exposed_with`
  searches tool *result* text, and a description never appears in one, so the case would have
  reported "never exposed" for text in front of the model all run — an injection case that can
  only pass. `exposed_in_tools` reads the definitions the registry produced, since the event log
  records the allowlist by name only.
- **The orphan prediction was wrong.** The plan and the adapter both assumed a `kill -9`'d worker
  strands its stdio children. Measured, the OS closes the pipe and a well-behaved server exits on
  EOF. The real caveat is a server that ignores EOF, and there is still no boot sweep.
- **Exit criterion 4 is measured, and it is partially met.** With a `COURTLISTENER_TOKEN` the pull
  ran until the daily quota cut it off at 109 documents — 84 distinct cases, not the 2,500 the plan
  budgeted for. The table is now measured on a real corpus with a correctly-constructed label set,
  and `results-scotus.json` carries the corpus size that produced it. But **84 documents is roughly
  30× too few for recall@8 to discriminate**: top-8 of 84 documents is the top 9.5% of the corpus,
  where the plan assumed 0.3%. `recall@8` saturates at 1.000 for vector and hybrid exactly as the
  12-opinion fixture did, and MRR is the only column that separates the modes. See "The corpus
  measurement, measured" below.
- **The duplicate problem was real, and was not the cause of the saturation.** CourtListener
  publishes each revision of an opinion as its own document; 25 of the 109 were revisions of
  something already present, and *Trump v. CASA* was 10.8% of the corpus by itself. Fixing it
  (ADR-39, `agentd dedupe`) was necessary for the measurement to be *valid* — it is what makes
  one-relevant-document-per-query the right labeling rather than a choice between two biases — but
  it moved the numbers by less than 0.03 in every cell. The corpus size is the binding constraint,
  not the duplicates.

## Goal

M6 is the milestone where the project stops being five milestones and becomes one thing a reader
can walk into.

That splits cleanly in two, and the halves should not be confused for each other:

- **One real mechanism is still missing.** The MCP adapter is the last piece of §8 and the only
  part of the tool system that has never been exercised against a peer this codebase does not own.
  It is code, it gets tests, and it is not decoration.
- **Everything else is presentation, and presentation is the deliverable.** The README is an
  853-line milestone journal whose first status line still says *"M4 complete. The eval harness is
  not implemented yet"* — which has been false since M5 landed. There is no architecture diagram,
  no `docs/ARCHITECTURE.md`, and no way to watch a run without `curl` and a terminal. The work in
  M1–M5 is real; a reader currently has to excavate it.

The viewer sits across both halves. It is nominally polish, but building it is the only thing that
has ever exercised the `Last-Event-ID` replay contract from a client that actually drops its
connection, which is the detail §13 says is worth building.

## What already exists (do not rebuild)

- **The whole §13 surface that is going to exist.** [`api.go:142`](../../internal/api/api.go#L142)
  already routes `/v1/tools`, `/v1/runs` POST, `/{id}`, `/{id}/events`, `/{id}/stream`,
  `/{id}/trace`, `/{id}/cancel`, `/{id}/resume`, plus `/healthz` and `/metrics`. M6 adds exactly one
  endpoint — the listing the viewer needs — and deliberately does not add `POST /v1/corpus/ingest`
  (see Decisions).
- **The `Tool` interface already has the seam.** [`tool.go:23`](../../internal/tools/tool.go#L23)
  defines `External` as a trust tier and the package doc names the MCP adapter as its user. The
  adapter implements `Tool` and registers like everything else; the registry, the schema
  validation, the allowlist, the envelope, the ledger, and the tracing all apply to it unchanged.
  If the adapter needs a change to `tools.Registry`, that is a signal the abstraction was wrong,
  not a licence to special-case MCP.
- **The envelope, and the reason it exists.** [ADR-33](../DECISIONS.md) and §10: tool results reach
  the model inside a labeled `<tool_result>` envelope that the system prompt declares to be data.
  MCP results are untrusted input of exactly the kind the envelope was built for, and they get it
  for free by going through the loop. What they do *not* get for free is covered under Design.
- **Ingest, as a working CLI path.** [`internal/retrieval/ingest.go`](../../internal/retrieval/ingest.go)
  and `agentd ingest` ([`retrieval.go:181`](../../cmd/agentd/retrieval.go#L181)) already do parse →
  chunk → embed → upsert with content-hash skipping and a concurrency flag. This is the whole
  feature; what M6 declines to build is an HTTP front door onto it.
- **The queue pattern.** `FOR UPDATE SKIP LOCKED`, leases, heartbeats, and a reaper are built and
  tested in [`worker.go`](../../internal/runtime/worker.go), and M6 adds no second consumer of it.
- **Every number the README needs.** The retrieval table, the two injection numbers, the eval
  scorecard, the crash GIF, and both Jaeger screenshots are already checked in. The README work is
  arrangement, not measurement — with one exception, the four-mode retrieval table, which is
  settled under Decisions and runs as build-order step 0.

## Exit criteria

1. `agentd work` and `agentd serve` load MCP servers from a config file, list their tools in
   `GET /v1/tools` with `trust_tier: "external"`, and an agent run completes a goal that requires
   calling one — end to end, through the allowlist, the envelope, and the ledger.
2. An MCP tool call that crashes its server mid-call produces a `tool_failed` the run recovers
   from, and a worker shutdown leaves no orphaned stdio subprocess.
3. Opening `http://localhost:8080/` lists recent runs; opening one streams its trajectory live,
   survives a killed connection without losing or duplicating a step, and links to its Jaeger
   trace. Killing the worker mid-run and starting a new one is visible in the viewer as it
   happens.
4. The four-mode retrieval table in the README is measured against a real CourtListener corpus and
   30–50 hand-labeled queries, and `evals/retrieval/results.json` carries the corpus size and model
   names that produced it. The §17 resume bullet no longer carries an HTML comment describing a
   measurement it cannot make. **Met, with the corpus 30× under target** — see the status note
   above: measured on 84 cases / 13,114 chunks / 40 labeled queries, `results-scotus.json` carries
   both, and the §17 comment now records the caveats rather than a missing measurement. Recall@k
   saturates at that corpus size, so MRR carries the result.
5. `docs/ARCHITECTURE.md` exists, the README opens with what the project is and an architecture
   diagram rather than with M1, and its status line is true. The README states that ingest is a CLI
   operation by design and why, rather than listing it as deferred.
6. `make test`, `make eval`, and `make eval-retrieval` are green, and the new code is covered by
   the test matrix below.

## Design

### The MCP adapter

Use the official SDK: `github.com/modelcontextprotocol/go-sdk`, currently v1.8.0 — a stable v1,
which is the whole argument. Hand-rolling JSON-RPC framing, initialization, and capability
negotiation would be several hundred lines of code that demonstrates nothing the adapter itself
does not, and it would drift from the spec the moment the spec moves.

New package `internal/tools/mcp`. Two types:

- `Client` — one connected MCP server. Owns the transport, the session, and the discovered tool
  manifest. Knows how to reconnect.
- `Tool` — one discovered tool, implementing `tools.Tool`. `Schema()` returns the server's
  `inputSchema` verbatim, `TrustTier()` returns `External`, `Invoke` does `tools/call` and
  flattens the content blocks into `Result.Content`.

Both transports §8 names: **stdio** (spawn a subprocess, speak over its pipes) and **streamable
HTTP**. Stdio is the one that gets the in-repo test server and the demo; HTTP is a second
`Transport` construction and a config field, and costs almost nothing once stdio works.

**Names are namespaced.** A discovered tool registers as `<server>__<tool>`. Two reasons, and the
second is the real one: an MCP server can name a tool `finish`, and `Registry.Register` rejects
duplicates at boot, so an unlucky server would turn a working binary into one that panics on
startup. Namespacing means a server can never shadow or collide with a builtin, and a run's
allowlist can name exactly which server's capability it grants.

**Discovery happens at boot, not per run.** This is forced by an invariant already in the code:
[`main.go:97`](../../cmd/agentd/main.go#L97) says `serve` and `work` must agree on the registry's
names, because [`normalizeConfig`](../../internal/api/api.go) fills a run's default allowlist from
the API's registry and rejects unknown tools at submission. So both processes read the same MCP
config file and both connect at boot. `serve` needs only the manifest — it lists and allowlists,
it never invokes — but it must connect to get one.

That leaves a failure mode worth being explicit about rather than papering over: **a server that is
unreachable at one process's boot and reachable at the other's makes the two registries disagree.**
The precedent is the sandbox, which [`buildSandbox`](../../cmd/agentd/main.go#L243) treats as a
warning rather than a fatal error, so runs that never touch it keep working. MCP takes the same
shape — an unreachable server logs a warning and contributes no tools — with the consequence
stated: a run submitted while the server was up and dispatched while it was down fails that tool
call with `unknown tool`, which the loop already reports to the model as a non-retryable tool
failure and which the model can route around. A run is never silently given a capability it was
not granted, which is the property §10 actually cares about.

**Cancellation and timeouts.** External gets a per-call timeout like the sandbox does, and honours
context cancellation, because [ADR-25](../DECISIONS.md) made cancellation interrupt in-flight work
rather than wait for it. A stdio server that hangs must not hold a cancel for longer than the
timeout.

**Lifecycle.** The worker spawns stdio subprocesses at boot and kills them on shutdown, including
on the paths where the worker is shutting down because of an error. A server that dies mid-call
fails that call and is reconnected lazily on the next one — exponential backoff, not a hot loop.
The worker already sweeps orphaned sandbox containers at boot; the stdio equivalent is that the
subprocess is a child of the worker and dies with it, which `kill -9` does not guarantee, so the
demo script should show what a leaked server looks like if it does.

**A demo server, in-repo.** Tests must not need `npx`, node, or the network. Ship a small MCP
server under `internal/tools/mcp/testserver` (or `cmd/agentd mcp-demo` if it is worth demoing by
hand) exposing two or three tools with real schemas — something in the legal-research shape, so the
demo goal reads naturally. The README then points at how to wire a real third-party server next to
it, which is the part a reader wants to see is possible.

### MCP tool descriptions are a new injection surface

This is the part of M6 that is genuinely a security decision rather than plumbing, and it belongs in
`SECURITY.md`.

§10's threat model is about *retrieved content*: a court opinion containing text that reads as an
instruction. The envelope answers it, and [ADR-33](../DECISIONS.md) hardened the envelope against
forging its own delimiters.

An MCP server introduces a second, differently-shaped surface. A tool's **name, description, and
JSON Schema** are written by the server operator and go into the model's tool definitions — which
is to say into the part of the request the system prompt's "content inside envelopes is data"
rule does not cover, because they are not inside an envelope. A hostile or compromised MCP server
can put an instruction in a tool description, and every model call for the rest of the run carries
it. This is the tool-poisoning attack, and the honest position is that **the envelope does not
defend against it and was never meant to**.

What M6 does about it:

- State it in `SECURITY.md` as its own threat, distinct from retrieved-content injection, with the
  trust boundary drawn where it actually is: an MCP server is configured by the operator at boot,
  like a binary on the PATH, and adding one is a trust decision equivalent to installing software —
  not equivalent to retrieving a document.
- Bound the blast radius with what already exists: a per-run allowlist fixed at submission means a
  poisoned description can only ask the model to use capabilities the run was already granted, and
  no tool with real side effects is reachable unless the run was configured for it.
- Add the cheap mechanical defences: cap description and schema size, and reject a server whose
  manifest changes shape under us mid-run.
- Add an `INJECTION` eval case with a deliberately poisoned MCP tool description, scored the way
  M5 scores the others — exposure first, then resistance ([ADR-30](../DECISIONS.md)).

The eval case is what makes this a claim with a number behind it rather than a paragraph.

### The trajectory viewer

One page, embedded in the binary with `go:embed`, served at `/`. No build step, no framework, no
CDN — plain HTML, CSS, and JavaScript. A portfolio project that needs `npm install` to show its own
output has added a dependency to save nothing.

It does two things:

1. **A run list.** Which needs an endpoint that does not exist: `GET /v1/runs?limit=&status=`,
   returning id, status, goal, spend, and timestamps, newest first. Without it the viewer opens on
   a box that wants a UUID pasted into it. It is a dozen lines over a table the store already reads.
2. **A trajectory.** Fetch `/v1/runs/:id/events` for history, then open `/v1/runs/:id/stream` with
   `Last-Event-ID` set to the last seq seen, and render events as they arrive: model turns, tool
   calls with their arguments and results, the step count, the token and cost counters against the
   budget, and the terminal status. A cancel button posting to `/{id}/cancel`, and a link out to
   `/{id}/trace`.

Two things it must get right, because they are the reasons to build it at all:

**Reconnect.** `EventSource` reconnects on its own and sends `Last-Event-ID` — which is precisely
the contract [`streamRun`](../../internal/api/api.go) implements and which no test currently
exercises from a client that really disconnects. Pull the network cable (or stop the API for two
seconds) mid-run and the trajectory must continue with no gap and no repeat. That is exit criterion
3, and it is the SSE-vs-WebSocket reasoning made concrete.

**Rendering untrusted text.** Tool results and model output are attacker-influenced by construction
— the corpus contains deliberately poisoned documents, and after the MCP work, so can a tool
description. Every dynamic string goes in through `textContent`, never `innerHTML`. Getting this
wrong would mean the project's own viewer is the thing that executes the injection its eval suite
exists to prove it resists, which is a bad enough irony to be worth a sentence in the README.

The third thing it should show, because it is the project's headline: **watching the crash demo
live**. Run `scripts/crash-demo.sh` with the viewer open and the run visibly stalls at the lease
gap, then continues under a new worker without re-running the completed tool call. That is a better
artifact than the GIF, and it can become the GIF.

## Build order (days 20+)

0. **Start the corpus before anything else.** `make fetch-corpus COURT=scotus LIMIT=2500`, then
   `make ingest`, on the morning of day 20. Roughly half an hour of rate-limited pulling and about
   an hour of unattended embedding — and `ingest` skips documents whose content hash already
   matches unless given `-force`, so an interrupted run resumes for free rather than restarting.
   Nothing below depends on it, and it is the only step whose cost is wall-clock rather than
   attention, which is the whole reason it goes first. Hand-label 30–50 queries in the gaps
   between steps 1 and 3 using `agentd eval retrieval -label "<query>"`, then `make eval-retrieval`
   before step 5 needs the table. *Demoable: a four-mode table whose rows differ.*
1. **MCP adapter, stdio.** SDK dependency, `Client`, `Tool`, namespacing, boot-time discovery, the
   in-repo test server, unit and integration tests. Wire into `registry()` for both `serve` and
   `work` behind an `-mcp-config` flag. *Demoable: `GET /v1/tools` lists an external tool and a run
   calls it.*
2. **MCP hardening.** HTTP transport, reconnect and backoff, timeouts and cancellation, subprocess
   lifecycle on shutdown, size caps on descriptions and schemas. `SECURITY.md` section and the
   poisoned-description eval case. *Demoable: kill the server mid-call, the run recovers.*
3. **`GET /v1/runs` + the viewer.** List endpoint, embedded page, history-then-stream, reconnect,
   cancel, trace link. *Demoable: the crash demo, watched live.*
4. **Docs.** `ARCHITECTURE.md`, README restructure, the redrawn diagram, a viewer screenshot,
   ADRs 34–37, a final pass over `SECURITY.md` and `DECISIONS.md`. Re-record the crash GIF from the
   viewer if step 3 made a better one.

## Explicitly not in M6

- **Auth on the viewer or the API.** §2 puts multi-tenancy, auth, and RBAC out of scope for v1, and
  a viewer that ships a login form implies a user model that does not exist. The README says the
  control plane assumes a trusted network.
- **MCP resources, prompts, sampling, or elicitation.** §8 asks for the client adapter to list tools
  and expose each as a `Tool`. Sampling in particular would let a server ask *this* runtime for a
  model call, which is a budget-attribution problem ([ADR-23](../DECISIONS.md)) and a trust problem
  and deserves its own milestone rather than a corner of this one.
- **Per-run MCP servers.** A run naming its own server to connect to would let a submission add a
  capability to the process, which inverts the trust boundary the previous section just drew.
  Servers are operator configuration.
- **A viewer that edits.** Cancel is the only write, because cancel is already a first-class run
  operation. Resubmit, edit-and-replay, and trajectory diffing are a different tool.
- **`LISTEN/NOTIFY`.** Still the right upgrade for the SSE tail's 200ms poll, and still not what M6
  is about. The viewer makes the case stronger by adding per-client cost, which is worth a sentence
  in the README rather than an implementation.
- **A cross-encoder reranker.** A second implementation of `rerank.Reranker`, deferred on price with
  the numbers behind it ([ADR-23](../DECISIONS.md)), and unchanged by this milestone.

## Decisions

### Settled 2026-09-14, before implementation

**The corpus measurement is in, and it runs as step 0.**

The question was never honesty. The README already states the caveat plainly — *"Read that table
for what it is: twelve well-known opinions with one query written per case is a smoke test, not a
benchmark"* — explains why every mode saturates, and prints the reproduction recipe. The disclosure
is done and it is well written. So this is a pure value decision about whether a real benchmark is
worth the time, not a choice between measuring and admitting.

It is worth it, because the cost is much lower than it looks and almost none of it is attention:

- The checked-in fixture is 12 synthetic one-paragraph summaries averaging 1,285 characters — 48
  chunks in total. Real opinions run 20–60k characters, so 2,500 of them at `Target: 1200` is on
  the order of **75,000 chunks**, roughly 1,500× the current corpus. Saturation breaks decisively;
  top-8 out of 75,000 is a selective question in a way top-8 out of 48 is not. SCOTUS is also the
  right jurisdiction for it, because its near-neighbour density is high: many Fourth Amendment
  cases that look alike is precisely the property that makes the four modes disagree.
- Fetch is ~30 minutes of rate-limited pulling. Embedding is ~1 hour, unattended, and resumable by
  content hash. The rerank mode is the slow eval — 388s for 13 queries on the fixture, so budget
  ~40 minutes for 40 queries on real chunks, and `-modes` runs them separately.
- **Only the labeling costs attention: about two hours.** Everything else is machine time that
  overlaps the MCP work, which is why step 0 starts on day 20 morning and the table lands exactly
  when step 5 needs it.

§9 asks for this directly, and is right about why: *"A table of those four numbers in the README is
worth more than any amount of architecture prose."* Without it the strongest available claim about
M3 is that hybrid search was built and the fixture is too small to say whether it helps — a weak
position for a milestone that took four days.

Two things to hold onto while doing it:

- **The numbers may not flatter the design, and that is fine.** Hybrid may barely beat vector; the
  LLM reranker may not beat hybrid at all. Report whatever comes out. A measured negative is a
  better signal than an assumed positive, and specifically: if the reranker costs ~1,000× the wall
  time for no recall gain, that converts [ADR-23](../DECISIONS.md)'s local-only rerank policy from
  a price argument into a measured one, which is strictly stronger.
- **Labeling bias matters far more at 2,500 documents than at 12.** The note already at the top of
  [`labels.yaml`](../../evals/retrieval/labels.yaml) — write about a third of the queries from
  documents picked off the corpus listing first, not from search results — is the difference
  between a real recall@8 and a flattering one that means nothing.

**The milestone journal lives in `docs/MILESTONES.md`, and it already moved.**

Done ahead of step 5, because it was blocking the shape of everything else in the README. The
journal and `ARCHITECTURE.md` are different documents for different readers and collapsing them
was the mistake the open question was circling: the journal is *narrative and contemporaneous* —
what M2 decided, which defect M5's evals caught, what the numbers were on the day — and
`ARCHITECTURE.md` is *current and atemporal*, describing the system as it stands. A reader asking
"how does resume work" should never have to infer it from what M1 said it would do.

So M1–M5 moved verbatim out of the README into [`MILESTONES.md`](../MILESTONES.md) with a table of
contents and relative paths repointed, `ARCHITECTURE.md` is still to be written in step 5 and takes
the design content rather than the history, and the README now opens on the project and its
Quickstart instead of on M1. The status line, false since M5 landed, is corrected. Sections are
kept as written rather than rewritten forward: where a later milestone changed something, the later
section says so, which is the property that makes a journal worth keeping.

**`POST /v1/corpus/ingest` is cut, and the invariant is why.**

§4 says the API server never calls a model — it writes intent and tails the event log, and all
execution happens in workers, which is what makes crash recovery mean anything. Ingest embeds, and
embedding is a model call. So the endpoint could never do the work in-process; it would have to be
a second queue: an `ingest_jobs` table and migration, store methods, a second claim path in the
worker, two handlers, progress reporting (an hour-long job you cannot poll is useless), and tests.
The worker side is genuinely small — [`Run`](../../internal/runtime/worker.go) has a clean
`claimAndExecute` seam — but the item as a whole is the second-largest thing in M6.

The question that settles it is what it would demonstrate that the project does not already
demonstrate, and the answer is nothing. An async job with a status poll is a worse version of the
runs API, which does the same thing over SSE. The `SKIP LOCKED` queue is proven. Leases are proven,
and an ingest job would deliberately skip the interesting half of them: it needs no fencing,
because ingest is already idempotent by content hash, where a tool call is not. What is left is
§13 completeness — an endpoint existing so a reader diffing the spec against the code finds all of
them.

Against that, the README gets to say ingest is a CLI operation *by design, because the API process
never calls a model*, and that is the stronger artifact. The invariant is the reason the endpoint
does not exist, which is better evidence for the invariant than building something that carefully
