# M3 plan — Retrieval

Spec reference: `agent-runtime-spec.md` §5 (`documents`, `chunks`), §8 (`search_corpus`,
`fetch_document`), §9 (retrieval), §10 (the corpus is untrusted input), §14 M3.

## Status: built (2026-09-09)

Everything below shipped. What changed from the proposal, and why:

- **The lexical query is OR-of-lexemes, not `websearch_to_tsquery`.** The proposal picked
  `websearch_to_tsquery` for its tolerance of natural-language input, which was the wrong
  property to optimise for: it *parses* a question without erroring but then ANDs every term, so
  a ten-lexeme question matches almost no 1,200-character chunk. The eval caught it as BM25
  recall@8 of 0.154. The query now normalises the question through the same dictionary that
  built the index and ORs the lexemes, leaving `ts_rank_cd`'s cover-density ranking to
  discriminate; recall@8 went to 1.000 on the same labels. `TestSearchLexicalVerboseQuery` is
  the regression test.
- **Sorting after rerank lives in the searcher, not the reranker.** `Reranker` returns scores
  and the searcher does the stable sort, so a degraded or partially-scored batch cannot silently
  reorder results and every implementation gets tie-breaking for free.
- **A degraded rerank is an error inside the eval, though not in the tool.** The tool falls back
  to the fused order and says `mode: "hybrid"`; the eval refuses to report a `hybrid+rerank`
  row that actually measured hybrid, because a mislabeled number in the README is worse than a
  missing one.
- **The checked-in eval numbers are a smoke test, and the README says so.** Twelve opinions with
  one query per case saturates every mode at recall 1.000. It is kept because it runs in seconds
  without a corpus pull and does catch breakage (it caught the AND bug), but the discriminating
  numbers need the CourtListener pull and hand-labeling, which is operator work, not code.
- **`agentd eval retrieval -label` shipped as planned** and is how the label set is meant to
  grow past the smoke fixture.

Decisions that departed from the spec's sketch, made up front so they could be argued with
before code existed:

- **The corpus comes from the CourtListener REST API, not the bulk CSVs.** The bulk export is
  one multi-gigabyte opinions file plus clusters, dockets, and courts files that have to be
  joined to filter by court; the REST API filters server-side
  (`cluster__docket__court=<id>`), pages by cursor, and needs a free token. A few thousand
  opinions is a few thousand requests, well inside the authenticated rate limit. The bulk path
  stays documented as the way to scale past that. ADR-17.
- **Recent Supreme Court opinions, capped at ~2,500.** Spec §9 says one jurisdiction and a few
  thousand opinions. `scotus` filtered to `filed_after=2010-01-01` gives clean text
  (`html_with_citations` is populated) and, more importantly, cases the person labeling the eval
  set already knows, which is what makes hand-writing 30 to 50 queries with known-relevant
  documents a two-hour job rather than a two-day one. Any court id works; it is a flag.
- **Embeddings come from Ollama's OpenAI-compatible `/v1/embeddings`**, model
  `mxbai-embed-large` (1024 dimensions, matching `VECTOR(1024)` in the schema; 512-token
  context, which bounds chunk size). Same runtime the worker already talks to, no new
  service. `bge-m3` is the drop-in alternative at the same width.
- **The reranker is an LLM reranker driven through the existing `model.Provider`**, not a
  cross-encoder. There is no Go cross-encoder runtime, and llama.cpp's `/v1/rerank` needs a
  second server. Pointwise relevance scoring through the provider seam reuses the local model
  that is already running, costs $0, and is one interface away from a cross-encoder later.
  ADR-19.
- **Fusion happens in Go, not SQL.** Two simple indexed queries (HNSW top 50, GIN top 50) and
  a twenty-line RRF over their results is easier to test in isolation and to report per-mode
  numbers from than one CTE that does everything. The eval needs the two lists separately anyway.
  ADR-18.
- **`POST /v1/corpus/ingest` is deferred.** Ingest is an operator action that takes minutes
  and needs the embedding runtime; it ships as `agentd ingest` (the spec's repo layout lists
  that subcommand). The HTTP endpoint is a thin async wrapper over the same code and lands
  with the other API polish in M6. This is a deviation from §13; called out in the README.

## Goal

A legal research question submitted as a run is answered from a real corpus of court opinions
with citations that resolve to real chunks, and the retrieval quality is measured, not
asserted.

**Exit criteria, as met.** 1, 2, 3 and 5 are done and verified. 4 is done as code and run for
real, but the reported numbers are a smoke test rather than a benchmark: against the checked-in
12-opinion fixture all four modes saturate at recall@8 = 1.000 (`mxbai-embed-large` embeddings,
`qwen2.5:7b` reranking, MRR 0.923 for BM25 alone). The table is in the README with that caveat
stated plainly. Producing discriminating numbers is not a code task — it needs the 2,500-opinion
CourtListener pull and two hours of hand-labeling, which the tooling (`fetch`, `ingest`,
`eval retrieval -label`, thresholds, `results.json`) is built and tested for.

Criterion 3 was verified end to end against a live worker and Ollama, not only in tests: a run
granted `search_corpus`, `fetch_document`, and `finish` searched, read Carpenter, and finished
with "…is a Fourth Amendment search (clop-0002 ¶1)", a pair that resolves to a real `chunks`
row. Original criteria:

1. `agentd fetch` pulls N opinions from one court into a JSONL file; `agentd ingest` chunks,
   embeds, and upserts them idempotently (re-running skips unchanged documents, re-embeds when
   the embedding model changes).
2. `search_corpus` returns the top 8 chunks for a query via vector + BM25 + RRF + rerank, each
   with document id, source id, title, court, date, section, and paragraph ordinal.
   `fetch_document` returns a document or a range of its chunks by id.
3. A run with the goal "What did the Court hold about X? Cite the opinion and paragraph" uses
   `search_corpus`, then `fetch_document`, then `finish`, against both the local model and
   Claude, and the final answer's citations are real `(source_id, ordinal)` pairs.
4. `make eval-retrieval` prints recall@8, recall@20, and MRR for vector-only, BM25-only,
   hybrid, and hybrid+rerank over a hand-labeled set of 30 to 50 queries, and exits nonzero
   below a threshold. The table goes in the README with the real numbers.
5. Tests: unit for chunking, RRF, HTML-to-text, the tools, the reranker parser; integration
   against pgvector for the store queries, ingest idempotency, and a full run through the loop
   with a fake model and fake embedder; README paragraph, ADRs, `SECURITY.md` update, this plan.

### Schema (migration 0002)

```sql
ALTER TABLE documents
  ADD COLUMN court          TEXT,
  ADD COLUMN decided_on     DATE,
  ADD COLUMN content_sha256 TEXT NOT NULL DEFAULT '',
  ADD COLUMN chunk_count    INT  NOT NULL DEFAULT 0,
  ADD COLUMN ingested_at    TIMESTAMPTZ;
CREATE INDEX documents_court_decided_idx ON documents (court, decided_on);

ALTER TABLE chunks
  ADD COLUMN section         TEXT,
  ADD COLUMN char_start      INT NOT NULL DEFAULT 0,
  ADD COLUMN char_end        INT NOT NULL DEFAULT 0,
  ADD COLUMN embedding_model TEXT,
  ADD CONSTRAINT chunks_document_ordinal_key UNIQUE (document_id, ordinal);
```

`court` and `decided_on` are columns rather than JSONB paths because the tools filter on them
and citations print them. Everything else CourtListener returns (docket number, reporter
citations, judges, cluster id, the URL) stays in `metadata`. `content_sha256` is the
idempotency key for ingest; `embedding_model` on every chunk row is what makes "which model
produced this vector" answerable, and what the ingest compares to decide whether to re-embed.

The GIN and HNSW indexes from 0001 are kept. HNSW builds incrementally on insert; at ~50k
chunks (2,500 opinions × ~20 chunks) that is minutes, not hours. Queries set
`hnsw.ef_search = 100` in the transaction so the top-50 candidate list is not starved by the
default of 40.

### Fetch

```
agentd fetch -court scotus -filed-after 2010-01-01 -limit 2500 -out data/corpus/scotus.jsonl
```

Two calls per opinion: the search endpoint (`type=o&court=<id>&filed_after=…`, ordered by date)
yields case name, date filed, docket number, citations, and opinion ids per cluster in one row;
`opinions/{id}/?fields=id,type,html_with_citations,plain_text` yields the text. Only the lead
opinion (`type` 010combined or 020lead) is taken so one document is one decision; dissents and
concurrences are a follow-up. `html_with_citations` is preferred, `plain_text` is the fallback,
empty text is skipped and counted. The client honours `Retry-After` on 429, resumes from an
existing output file (skips ids already written), and reads the token from `COURTLISTENER_TOKEN`.

Output is one JSON object per line: `{source_id, title, court, decided_on, text, metadata}`.
Ingest reads only this format, so the corpus source is swappable (a different court, the bulk
CSV, a synthetic poisoned set in M5) without touching the pipeline.

### Chunking

Structure first, size second (spec §9). Text is split on blank lines into paragraphs. A short
line in title case or all caps, or one starting with a Roman numeral or a letter and a period
(`II.`, `A.`), is a section heading; it is not a chunk of its own but is carried as `section`
on every chunk until the next heading. Consecutive paragraphs are merged until the chunk reaches
the target size; a single paragraph over the maximum is split at sentence boundaries. Overlap
is the last sentence of the previous chunk (capped) prepended to the next, so a holding that
straddles a boundary is retrievable from either side.

| Parameter | Value | Why |
|---|---|---|
| target | 1,200 chars (~300 tokens) | comfortably inside `mxbai-embed-large`'s 512-token window with the query prefix |
| max | 1,800 chars | hard cap; a paragraph longer than this is split at sentences |
| min | 200 chars | shorter trailing fragments are merged backward |
| overlap | last sentence, ≤ 200 chars | one sentence is enough to carry a straddling holding; more inflates the index |

`Chunk(text) []Chunk` is pure. Invariants asserted in tests: ordinals are `0..n-1` with no
gaps; `char_start/char_end` cover the input without loss (overlap excluded); no chunk exceeds
max; every chunk under a heading carries it.

### Embedding

```go
type Embedder interface {
    Embed(ctx context.Context, texts []string) ([][]float32, error)
    Model() string
    Dimensions() int
}
```

The OpenAI-compatible client posts `{model, input: [...]}` in batches of 32. Documents are
embedded bare; queries get `mxbai-embed-large`'s recommended prefix (`Represent this sentence
for searching relevant passages: `), applied by the searcher, not the caller, so the eval and
the tool cannot disagree. At worker boot the embedder is probed with one string and the result
width checked against the schema (1024); a mismatch is fatal, because a wrong-width vector fails
at insert time with a much worse message. An unreachable embedder is a warning (like the
sandbox): `search_corpus` calls then fail as retryable `tool_failed` until it is back.

The fake embedder hashes words into a fixed-width bag-of-words vector, so a test corpus has
real, deterministic nearest-neighbour structure without a model.

### Ingest

```
agentd ingest -file data/corpus/scotus.jsonl [-embed-model mxbai-embed-large] [-force]
```

Per document, in this order: compute `sha256(text)`; load the existing row by `source_id`; skip
if the hash, the chunk count, and the embedding model all match and `-force` is off; otherwise
chunk, embed every chunk (batched), and in **one transaction** upsert the document, delete its
chunks, insert the new ones, set `chunk_count` and `ingested_at`. A crash mid-corpus leaves
every completed document whole and every unstarted one absent; re-running finishes the rest.
Two documents are embedded concurrently by default (`-concurrency`); Ollama serialises
embedding calls anyway, so more only adds queueing.

A summary at the end: documents seen, skipped, ingested, failed; chunks written; wall time;
embed throughput. The same code path serves the test fixture and the real corpus.

### Search

```go
type Query struct {
    Text     string
    K        int        // final results, default 8
    Mode     Mode       // Vector | Lexical | Hybrid | HybridRerank (tool always uses the best available)
    Court    string     // optional filters
    From, To *time.Time
}
type Hit struct {
    ChunkID, DocumentID uuid.UUID
    SourceID, Title, Court, Section string
    DecidedOn *time.Time
    Ordinal   int
    Content   string
    Scores    struct{ VectorRank, LexicalRank int; RRF, Rerank float64 }
}
```

1. Embed the query (with prefix).
2. `SearchVector`: `SELECT … ORDER BY embedding <=> $1 LIMIT 50`, filters applied in the
   `WHERE`, `SET LOCAL hnsw.ef_search = 100`.
3. `SearchLexical`: `websearch_to_tsquery('english', $1)` against `tsv`, ranked by
   `ts_rank_cd`, `LIMIT 50`. `websearch_to_tsquery` tolerates natural-language queries and
   quoted phrases, which is what a model will send.
4. RRF with `k = 60`: `score = Σ 1/(k + rank)` over the lists a chunk appears in. Ties broken
   by vector rank, then chunk id, so results are deterministic.
5. Rerank the fused top 50 to top K (below). If the reranker is off or fails, the fused order
   is returned and the hit's `Rerank` score is absent; the tool result says which.

Steps 2 and 3 run concurrently. The four eval modes are the same code with steps skipped, so
"hybrid" in the README table is exactly what the tool does.

### Rerank

```go
type Reranker interface {
    Rerank(ctx context.Context, query string, cands []Candidate, topK int) ([]Scored, error)
}
```

The LLM reranker sends batches of 10 candidates to `model.Provider.Complete` with a system
prompt that asks for a relevance score 0–10 per candidate as JSON (`{"scores":[{"id":1,
"score":7},…]}`), temperature 0, `max_tokens` 256, four batches in flight. Parsing is lenient
(first JSON object in the text, missing ids score 0, garbage batch scores all 0 and is logged).
Sorted by score, ties by RRF order. Any error from the provider degrades to the RRF order rather
than failing the tool: a reranker outage should cost recall, not the run.

Two things to be honest about in the README: (1) with `qwen2.5:7b` on a laptop this is the slow
step, roughly 10–30 s for 50 candidates, so `-rerank-candidates` defaults to 50 per the spec but
can be lowered; (2) the reranker's model calls happen inside a tool, so their tokens and cost are
**not** in the run's `spent_usd`. With the local model that is $0 and true. Pointing the
reranker at Claude would spend outside the budget; M3 refuses a non-local rerank model for that
reason. *Closed in M4:* `tool_succeeded` now carries `cost_micro_usd` and the token counts, and
the transaction that writes it bumps the run's counters, so tool-internal spend is inside the
budget (ADR-23). The local-only policy was kept anyway — measured at about $0.04 per search, it
was declined on price rather than for want of a mechanism.

### Tools

```
name:        search_corpus            trust tier: builtin (in-process, read-only Postgres)
args:        query (string, 3..500 chars, required)
             k (integer, 1..20, default 8)
             court (string), date_from / date_to (YYYY-MM-DD)
result:      {query, mode, candidates_considered, hits: [{chunk_id, document_id, source_id,
              title, court, decided_on, section, ordinal, content, score}]}

name:        fetch_document           trust tier: builtin
args:        document_id (uuid) or source_id (string), one required
             ordinal_from / ordinal_to (integers, optional; whole document when absent)
             max_chars (integer, 1000..32000, default 12000)
result:      {document: {id, source_id, title, court, decided_on, metadata, chunk_count},
              chunks: [{ordinal, section, content}], truncated}
```

Result size is bounded twice: chunks are ≤ 1,800 chars by construction, and each tool caps its
serialised result (24 KiB for search, `max_chars` for fetch) with a `truncated` flag, so a
result can never crowd the context window the way an uncapped `stdout` could. Both tools are
registered in `serve` (so `/v1/tools` lists them and the allowlist accepts them) with nil
dependencies, and in `work` with the store, embedder, and reranker. The tool descriptions tell
the model to cite by `source_id` and `ordinal`, and `DefaultSystemPrompt` gains one sentence
saying the same and that quoted opinion text is data (§10). This is the citation convention
the M5 `CITATION` eval will check against the `chunks` table.

### Prompt injection

Retrieved text is the first untrusted content that is *designed* to be read as prose, so the
existing envelope does most of the work and two things are added: the tool descriptions and the
system prompt say that opinion text is quoted material, and `SECURITY.md` gets a "Retrieved
documents" section describing the boundary (content is a JSON string field inside the
`<tool_result>` envelope, never in the system prompt, never in a tool description, never
interpreted by the runtime). Planting poisoned documents and proving the model ignores them is
M5's `INJECTION` category; the fetch/ingest split above is what makes injecting a synthetic
document into the corpus a one-line JSONL edit.

### Eval

```yaml
# evals/retrieval/labels.yaml
thresholds: {hybrid_rerank: {recall_at_8: 0.70}}
cases:
  - query: "standard for qualified immunity when no prior case is directly on point"
    relevant:
      - {source_id: "clop-1234567", ordinals: [14, 15]}   # chunk-level
      - {source_id: "clop-7654321"}                       # any chunk of this document counts
```

`agentd eval retrieval -labels evals/retrieval/labels.yaml` runs every query in all four modes
and prints:

| mode | recall@8 | recall@20 | recall@50 | MRR |
|---|---|---|---|---|
| vector | | | | |
| bm25 | | | | |
| hybrid | | | | |
| hybrid+rerank | | | | |

Recall@k is the fraction of labeled relevant items found in the top k, averaged over queries;
MRR uses the rank of the first relevant hit. Results are also written to
`evals/retrieval/results.json` with the corpus stats and the embedding and rerank model names,
so the README numbers are reproducible. Exit is nonzero if any threshold in the file is missed,
which is the `make eval` regression hook M5 will fold in.

Labeling help: `agentd eval retrieval -label "<query>"` prints the top 20 hybrid hits with
source id, ordinal, title, and a snippet, so a person can mark relevant ones and paste them
into the YAML. The rankings used for labeling should not be the only source of candidates
(that biases recall upward), so for a third of the queries the relevant document is chosen
first from the corpus listing and the query written from the opinion, not the reverse.

Wall time for the eval: four modes × 40 queries, of which only the rerank mode calls the model,
~40 × 15 s ≈ 10 minutes on a laptop. Acceptable for a number that goes in a README; the three
model-free rows run in seconds and are the ones to iterate on.

### Wiring

Worker flags and env: `-embed-url` (`AGENTD_EMBED_URL`, default the model URL), `-embed-model`
(`AGENTD_EMBED_MODEL`, `mxbai-embed-large`), `-rerank-model` (`AGENTD_RERANK_MODEL`, default
the worker's `-model`, must route to the local provider), `-rerank-candidates` (50),
`-rerank=off`. Compose passes them through. Makefile targets: `model-pull` also pulls the embed
model; `fetch-corpus COURT=scotus LIMIT=2500`; `ingest`; `eval-retrieval`; `demo-legal` (a
research question against the ingested corpus); `test-retrieval` (the pgvector integration
tests alone). `data/` is gitignored; `evals/retrieval/fixture.jsonl` and `labels.yaml` are not.

If time runs short, the reranker is the thing to cut (spec §14), in this order: ship the
three-row table without the rerank row, keep the interface and the `Noop`.

## Explicitly not in M3

`POST /v1/corpus/ingest` (M6, see above); poisoned documents and the `INJECTION` eval (M5, the
JSONL seam is ready for it); citation validation of final answers (M5 `CITATION`); a
cross-encoder or llama.cpp `/v1/rerank` backend (the `Reranker` interface is the seam); dissents
and concurrences as separate documents; query rewriting or multi-query expansion.

Two items on this list were M4's and have since landed: the `retrieval.search` span (with a
child per stage, so the reranker's share of search latency is visible rather than asserted) and
retrieval metrics; and attributing reranker cost to the run.

## Open questions for the author

Recommendations are baked in above; these are the ones worth overriding early rather than late.

1. **Court and cutoff.** `scotus` from 2010 is recommended for labeling ease. A state supreme
   court would be more "legal-tech" but makes the labeling harder for someone who does not
   practice there.
2. **Embedding model.** `mxbai-embed-large` (1024) is recommended; `bge-m3` (1024, 8k context)
   if longer chunks turn out to matter. Both fit the schema; switching is a re-ingest.
3. **Label granularity.** Chunk-level labels (spec wording) with document-level allowed as a
   fallback. If labeling time is the constraint, document-level for all 40 and a note in the
   README is defensible.
