# M1 plan — Real loop + durability

Spec reference: `agent-runtime-spec.md` §5 (data model), §6 (loop), §8 (tools), §10 (injection envelope), §13 (API), §14 M1.

## Status: implemented (2026-09-03)

Steps 1–6, 8, 9 (minus the GIF) and 10 are done and green: `make test` passes, and the resume
tests pass five consecutive runs. What changed from the plan below while building:

- **Ledger and event are one transaction.** `CompleteToolCall` writes the `tool_calls` row and
  the `tool_succeeded`/`tool_failed` event together, so the "replay from ledger" branch in the
  loop is defensive only and the planned "replay from ledger" test is moot. ADR-4 records this.
- **The loop reduces from the log every iteration** instead of after the model step only. The
  incremental version shipped a stale-messages bug that the tests caught. ADR-9.
- **`POST /cancel` landed in M1** after all: it is five lines once `RequestCancel` exists, and
  the loop already honoured the flag. M4 keeps the metrics side of cancellation.
- **`FinishRun` writes the event and the status in one transaction**, which the M0 ordering
  note (status before event) is now moot for.
- **Shared testcontainers fixture** (`internal/testutil`) boots one container per test binary
  and gives each test its own database, instead of a container per test.

Verified against a real model on 2026-09-03 (Ollama, `qwen2.5:7b`): `make test-live` passes and
`make crash-demo` shows worker B resuming after `kill -9` with the first tool call replayed
from the log, not re-executed. The recording lives at `docs/crash-demo.gif`, produced by
`vhs deploy/demo.tape`.

## Goal

Replace the M0 stub with the real agent loop, driven by `Reduce(events)`, talking to a local model
through a `ModelProvider` interface, calling one builtin tool through a registry, with leases,
heartbeats, a reaper, and the `kill -9` resume demo. Exit criteria:

1. A run against a local model (Ollama / llama.cpp, OpenAI-compatible endpoint) completes with at
   least one real tool call and a `finish` call.
2. `kill -9` a worker mid-tool-call, start a new worker, the run finishes and the already-completed
   tool call is not re-executed. Proven by an integration test **and** a recorded terminal demo.
3. `Reduce` has table-driven unit tests; the loop has integration tests against real Postgres.
4. README has an M1 paragraph; `docs/DECISIONS.md` exists with the M1 ADRs.

## What M0 already gives us (do not rebuild)

- `store.ClaimRun` with `FOR UPDATE SKIP LOCKED`, already claims expired-lease runs.
- `store.Heartbeat`, `store.FinishRun`, `store.AppendEvent` (per-run row lock, `max(seq)+1`).
- Worker skeleton: claim → heartbeat goroutine → execute → finish; on ctx cancel leaves the lease
  to expire (this *is* the crash path, keep it).
- SSE tail with `Last-Event-ID`, `/v1/runs/:id/events`.
- Event type constants in `internal/runtime/events.go`.

## Design decisions (go in `docs/DECISIONS.md`)

1. **Canonical message format is content blocks** (`text`, `tool_use`, `tool_result`), Anthropic-shaped.
   The local provider translates to/from OpenAI chat-completions on the wire. M1.5 then plugs the
   Anthropic provider in with near-zero translation, and the `model_responded` payload ("content
   blocks, stop reason, usage") is provider-independent.
2. **Local provider speaks OpenAI-compatible `/v1/chat/completions`**, not Ollama's native API.
   Ollama, llama.cpp `llama-server`, and vLLM all expose it with `tools` and `usage`, so one
   client covers every local runtime. Default model `qwen2.5:7b` (reliable tool calling on a Mac).
3. **Model calls are at-least-once, tool calls are exactly-once.** A crash between
   `model_requested` and `model_responded` re-issues the model call on resume (no side effects,
   cost is re-accounted honestly). A crash after a tool's result is committed never re-executes it,
   because the result commit and the `tool_succeeded` event are one transaction keyed by
   `(run_id, seq)`. A crash *during* execution re-executes; true exactly-once for side-effecting
   tools needs the tool to honor the `(run_id, seq)` idempotency key it is handed.
4. **Every write is fenced by the lease.** Append/update transactions lock the run row with
   `WHERE id=$1 AND lease_owner=$2`. A worker that lost its lease (paused, not killed) gets
   `ErrLeaseLost` and stops, so two workers can never interleave events on one run.
5. **Cost is carried as integer micro-USD** in Go and cast to `numeric` in SQL, so `spent_usd`
   never drifts from float rounding. Local pricing is 0; the fake provider in tests uses nonzero
   pricing to exercise the budget path.
6. **Reaper is explicit even though `ClaimRun` already picks up expired leases.** It flips
   expired `running` runs back to `queued` on a timer, logs it, and is the hook for the M4 metric.
   `ClaimRun` keeps the expired-lease clause as the fast path.

## Core types

```go
// internal/model/provider.go
type Role string // "user" | "assistant"

type ContentBlock struct {
    Type      string          `json:"type"`                 // text | tool_use | tool_result
    Text      string          `json:"text,omitempty"`
    ToolUseID string          `json:"tool_use_id,omitempty"`
    Name      string          `json:"name,omitempty"`
    Input     json.RawMessage `json:"input,omitempty"`      // tool_use args
    Content   string          `json:"content,omitempty"`    // tool_result body (enveloped)
    IsError   bool            `json:"is_error,omitempty"`
}
type Message struct { Role Role; Content []ContentBlock }
type ToolDef struct { Name, Description string; InputSchema json.RawMessage }
type Usage struct { InputTokens, OutputTokens int64 }

type Request struct {
    Model       string
    System      string
    Messages    []Message
    Tools       []ToolDef
    MaxTokens   int
    Temperature *float64
}
type Response struct {
    Model      string
    Content    []ContentBlock
    StopReason string // end_turn | tool_use | max_tokens
    Usage      Usage
}

type Provider interface {
    Name() string
    Complete(ctx context.Context, req Request) (*Response, error)
    // CostMicroUSD prices a call. Local returns 0. Anthropic (M1.5) uses a table.
    CostMicroUSD(model string, u Usage) int64
}
```

```go
// internal/tools/tool.go
type TrustTier int // Builtin | Sandboxed | External

type Invocation struct {
    RunID uuid.UUID
    Seq   int32           // idempotency key: seq of the tool_requested event
    Args  json.RawMessage
}
type Result struct {
    Content  json.RawMessage // returned to the model, enveloped by the loop
    ExitCode int
    Terminal bool            // finish sets this
}
type Tool interface {
    Name() string
    Description() string
    Schema() json.RawMessage
    TrustTier() TrustTier
    Invoke(ctx context.Context, inv Invocation) (Result, error)
}
```

```go
// internal/runtime/reduce.go
type State struct {
    Status          string            // derived: running until run_finished
    Steps           int               // count of model_responded
    Messages        []model.Message   // rebuilt conversation
    PendingTools    []PendingTool     // tool_use blocks with no tool_succeeded/failed yet
    ModelInFlight   bool              // dangling model_requested (crash window)
    SpentMicroUSD   int64
    InputTokens     int64
    OutputTokens    int64
    CancelRequested bool
    FinalAnswer     string
    LastSeq         int32
    Config          AgentConfig       // from run_started snapshot
}
func Reduce(events []store.Event) (State, error)
```

`AgentConfig` (parsed from `runs.agent_config`): `model`, `system_prompt`, `tools` (allowlist,
fixed at submission), `max_tokens`, `tool_delay_ms` (demo/test only, documented as such).

## Typed event payloads

| Event | Payload struct |
|---|---|
| `run_started` | goal, agent_config snapshot, max_steps, budget_usd, worker |
| `model_requested` | step, model, messages_sha256, params |
| `model_responded` | step, model, content blocks, stop_reason, usage, cost_micro_usd |
| `tool_requested` | tool_use_id, name, args |
| `tool_succeeded` | tool_use_id, name, result, duration_ms, exit_code, replayed (bool) |
| `tool_failed` | tool_use_id, name, error, retryable |
| `budget_exceeded` | spent_micro_usd, budget_micro_usd |
| `cancel_requested` | source |
| `run_finished` | status, final_answer |

`replayed: true` on `tool_succeeded` is how the resume path marks "result reused from the ledger"
so the demo and the RESILIENCE eval can assert it from the log alone.

## The loop (`internal/runtime/loop.go`)

```
events := store.ListEvents(run)
if len(events)==0: append run_started
state := Reduce(events)
for {
  if state.CancelRequested   → finish(cancelled)
  if state.Steps >= MaxSteps → finish(failed, "step limit")
  if state.Spent >= Budget   → append budget_exceeded; finish(budget_exceeded)

  // 1. drain pending tool calls first (resume lands here after a crash mid-tool)
  for each pending tool_use:
     row := store.GetToolCall(run, seq)
     if row.status == succeeded: append tool_succeeded{replayed:true} from row.result; continue
     if not allowlisted / unknown / schema invalid: append tool_failed{retryable:false}; continue
     result, err := tool.Invoke(ctx, Invocation{run, seq, args})   // with tool_delay_ms if set
     store.CompleteToolCall(run, seq, result|err)  // ledger update + event, one tx
     if result.Terminal: finish(succeeded, answer); return

  // 2. model step
  append model_requested{step, messages hash}
  resp := provider.Complete(ctx, Request{system, state.Messages, registry.Defs(allowlist)})
  store.AppendModelResponse(run, resp, cost)      // event + counters, one tx
  if resp.StopReason == end_turn && no tool_use: finish(succeeded, text)
  for each tool_use in resp:
     append tool_requested + INSERT tool_calls(status=started) ON CONFLICT DO NOTHING, one tx
  state = Reduce(reload)   // or fold incrementally; reload keeps it obviously correct for M1
}
```

Rules:
- Tool results enter `Messages` as `tool_result` blocks whose `Content` is the §10 envelope:
  `<tool_result tool="compute_deadline" seq="7">…</tool_result>` plus the system prompt line that
  says envelope contents are data, never instructions.
- Tool errors (unknown tool, bad args, tool returned err) go back to the model as
  `tool_result{is_error:true}`; they do not fail the run. The step limit bounds retries.
- Unknown `stop_reason`/`max_tokens` with no tool_use: treat as `end_turn`.
- Every loop write goes through fenced store methods; `ErrLeaseLost` aborts execution silently
  (the other worker owns the run now).

## Store changes

- `withRunLock(ctx, runID, owner, fn(tx))`: `SELECT 1 FROM runs WHERE id=$1 AND lease_owner=$2 AND finished_at IS NULL FOR UPDATE` → `ErrLeaseLost` on no row.
- `appendEventTx(tx, ...)` internal; `AppendEvent` gains an `owner` param and uses the lock.
- `AppendModelResponse(ctx, runID, owner, payload, usage, costMicroUSD)`: event + `UPDATE runs SET spent_usd = spent_usd + $cost::numeric/1e6, input_tokens += , output_tokens +=`.
- `RequestToolCall(ctx, runID, owner, payload)`: append `tool_requested` and `INSERT INTO tool_calls ... ON CONFLICT DO NOTHING` in one tx; returns seq.
- `GetToolCall(ctx, runID, seq)`.
- `CompleteToolCall(ctx, runID, owner, seq, status, result, eventType, payload)`: `UPDATE tool_calls` + append event, one tx.
- `ReapExpiredLeases(ctx) (int64, error)`: `UPDATE runs SET status='queued', lease_owner=NULL, lease_expires_at=NULL WHERE status='running' AND lease_expires_at < now()`.
- `ReleaseLease(ctx, runID)` for `POST /resume`: same update for one run regardless of expiry.
- `FinishRun` also fenced by owner.
- No new migration needed; schema from M0 already has everything.

## Worker changes

- `WorkerConfig` gains `Provider model.Provider`, `Registry *tools.Registry`, `DefaultModel`,
  `ReaperInterval` (default `LeaseDuration/2`). `StepDelay` removed.
- Heartbeat: on `!ok` (lease lost) **cancel the execution context** instead of just returning.
- Reaper goroutine started in `Run`, one per worker (idempotent, so two workers is fine).
- `claimAndExecute` calls `Loop.Execute(ctx, run)`; on `ErrLeaseLost` returns without `finish`.

## API changes

- `GET /v1/runs/:id` → `{ "run": Run, "state": State }` (reduce on read).
- `POST /v1/runs/:id/resume` → `ReleaseLease`; 409 if the run is terminal.
- `GET /v1/tools` → registry listing with name, description, schema, trust tier.
- `POST /v1/runs/:id/cancel` is deferred to M4 with the rest of cancellation; the loop already
  honors `cancel_requested` so M4 is endpoint-only.

## Crash demo (`scripts/crash-demo.sh`)

1. `make up` (postgres + jaeger + api), ollama running on host.
2. Start worker 1 in the background with `-lease 5s`, capture PID.
3. Submit a run whose `agent_config.tool_delay_ms = 8000` and a goal that forces a tool call
   ("Compute the filing deadline 30 court days after 2026-09-03, then finish").
4. Tail SSE in the background; wait for the second `tool_requested`.
5. `kill -9 $PID`. Show `GET /v1/runs/:id` still `running` with a lease owner.
6. Start worker 2. Within ~5s it claims, replays, finishes. Show the event log: one
   `tool_succeeded` for the first tool, the second tool re-executed, `run_finished`.
7. Record with `vhs` (`deploy/demo.tape`) → `docs/crash-demo.gif`. If `vhs` is not installed,
   `asciinema` + `agg` is the fallback; the script itself does not depend on either.

## Risks and mitigations

- **Small local models call tools unreliably.** The loop never depends on the model behaving:
  text-only `end_turn` is a valid success, bad tool calls become `is_error` results, `max_steps`
  bounds the damage. The demo goal is phrased to make the tool call obvious. If `qwen2.5:7b` is
  flaky, `llama3.1:8b` is the next choice; both are configurable via `-model`.
- **Crash window is hard to hit by hand.** `tool_delay_ms` in `agent_config` widens it for the
  demo; the integration test uses a blocking fake tool instead, so the test is deterministic.
- **Ollama not installed on this machine.** Steps 1–6, 8, 9 need no model at all (fake provider).
  Only step 7's live test and the demo need it.
- **Docker required for integration tests.** Already true for M0's testcontainers suite.
- **Lease stolen while a tool is mid-flight on a paused worker.** Fencing (decision 4) makes
  the stale worker's commit fail; the tool may have run twice, which is the documented
  at-least-once boundary for non-idempotent tools.

## Explicitly not in M1

Anthropic provider (M1.5), Docker sandbox and the `python` tool (M2), retrieval tools (M3),
`/cancel` endpoint, OTel spans, Prometheus (M4), cassettes (M5), MCP adapter (M6). The `Provider`
interface, event payloads, and the `Tool` interface are designed so none of those require
changing the loop or the log schema.
